# AJENDA-AI Outbound Communication Policy

**Status:** Planned (Bundle 6.1 policy baseline)  
**Effective date:** May 27, 2026  
**Owner:** Security/Governance + Growth Operations  
**Last reviewed:** May 27, 2026  
**Source-of-truth precedence:** Implementation/tests/runtime proof > PROJECT_SPEC.md > architecture docs

---

## 1) Purpose

This policy governs outbound GTM communication actions (drafting, send, publish, follow-up) to ensure safe, compliant, auditable, and tenant-scoped operation.

---

## 2) Scope

Applies to:

- outbound email or social direct-message flows
- content publishing to external channels
- follow-up sequencing and cadence decisions
- outbound communication artifacts generated by mission tasks

Does not grant autonomous execution authority; runtime execution still requires queue/lease authority and policy-approved admission.

---

## 3) Policy objectives

1. Prevent policy-unsafe outbound actions before queue admission.
2. Ensure explicit human-gate controls for high-risk communications.
3. Preserve tenant isolation and channel authorization boundaries.
4. Require evidence-backed traceability for every outbound decision.
5. Enforce fail-closed behavior on policy ambiguity or missing context.

---

## 4) Policy risk classes

| Risk class | Description | Default approval mode | Default runtime posture |
|---|---|---|---|
| `low` | Informational drafts with no external send/publish effect | `none` | allowed (draft-only) |
| `moderate` | Personalized draft generation or scheduling recommendations | `required` | allowed with review checkpoint |
| `high` | External send or publish action with potential brand/compliance impact | `multi_party_required` | denied unless explicit approvals and feature flags are enabled |
| `critical` | Regulated or materially sensitive outbound actions | `multi_party_required` + governance override | denied by default |

---

## 5) Required preconditions for outbound runtime admission

All outbound-send and publish-capable tasks must satisfy:

1. valid tenant context and tenant-auth envelope
2. capability risk class and side-effect class declared
3. policy profile resolved and evaluation status `allow`
4. approval checkpoint status `approved` (or stricter requirement)
5. channel authorization present for target integration
6. idempotency and retry safety metadata present
7. evidence contract fields complete

Any missing precondition requires fail-closed denial before queue enqueue.

---

## 6) Hard denials

The system must deny outbound admission when any of the following is true:

- tenant or principal mismatch
- unknown schema version or unrecognized policy profile
- missing provenance for sensitive claims
- prohibited recipient segment per tenant policy
- communication frequency exceeds policy/cadence ceiling
- high/critical action requested without required approval proof
- feature flag for outbound automation is disabled

---

## 7) Human-gate requirements

1. `external_send` and `external_publish` actions require explicit human approval.
2. High-risk campaigns require at least two independent approvers when configured (`multi_party_required`).
3. Approval records must include actor id, timestamp, policy version, and decision rationale.
4. Expired approval windows invalidate admission and require re-approval.

---

## 8) Evidence and audit requirements

Each outbound decision path must record:

- mission/task identifiers
- capability and adapter identifiers
- policy decision id, policy profile, and policy version
- approval artifacts and approver identity where required
- channel action envelope metadata (sanitized)
- execution outcome and error class where applicable

Evidence must be tenant-scoped, immutable-at-rest per retention class, and queryable for review.

---

## 9) Rollout and enforcement phases

Phase sequence:

1. **Observe-only:** policy evaluations logged, no hard blocks except explicit deny rules.
2. **Soft-enforce:** policy warnings block only high/critical risk classes.
3. **Hard-enforce:** full fail-closed denial for all missing preconditions.

Progression to stricter phases requires validation matrix proof and governance sign-off.

---

## 10) Compatibility and change control

- Policy keys and enums evolve additively.
- Existing policy profiles must keep semantic compatibility across minor versions.
- Breaking policy shifts require explicit version increment and migration guidance.
- Runtime behavior changes tied to this policy must ship with contract tests and rollback notes.
