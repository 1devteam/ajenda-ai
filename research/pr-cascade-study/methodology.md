# Initial Analysis Methodology

**Version:** 0.1 — 2026-08-24

## Objective

Build a reproducible PR causality graph and overlay it with architectural dependency information to measure corrective cascades, rework, blast-radius mismatch, and graph-assisted change outcomes.

## Phase 1 — PR census

Enumerate all Ajenda pull requests and capture at minimum:
- PR number/title/state;
- created/merged timestamps;
- base/head/merge SHAs;
- additions/deletions/files changed;
- description;
- changed filenames;
- reviews/comments where relevant;
- CI/test evidence where available.

Separate merged production PRs from unmerged/closed PRs and research instrumentation.

## Phase 2 — Candidate causal-edge discovery

Generate candidate edges using high-recall signals including:
- explicit references to earlier PR numbers;
- phrases such as follow-up, regression, fixes, restores, closes hole, hardens, reconcile, revert, supersede;
- direct merge ancestry;
- overlapping changed contracts/components;
- tests explicitly added for behavior introduced immediately prior;
- later corrections to newly introduced schemas, middleware ordering, authority boundaries, state transitions, or integration contracts.

Candidate generation is not classification.

## Phase 3 — Causal classification

Apply `definitions.md` to every candidate. Preserve evidence, alternative explanations, and uncertainty. Do not infer causation from temporal adjacency or file overlap alone.

Prefer Grade A evidence. Grade B requires diff-level validation. Grade C is retained separately as exposure rather than introduced defect.

## Phase 4 — Cascade graph

Construct a directed graph whose nodes are merged PRs and whose edges are classified causal repair/exposure relationships. Calculate:
- connected corrective cascades;
- depth/width;
- corrective descendants;
- time and PR distance to closure;
- recurrence by subsystem and contract type.

## Phase 5 — Architectural overlay

Map PR changes onto Ajenda's dependency/semantic graph where historically valid. For pre-graph periods, reconstruct architecture from repository state at relevant revisions where feasible rather than projecting current topology backward without qualification.

Measure:
- dependency centrality;
- change centrality;
- corrective/failure centrality;
- boundary crossings;
- affected tests/proofs;
- estimated/observed blast radius.

## Phase 6 — Scope mismatch analysis

For cascade origins, compare evidenced original reasoning/validation scope with retrospectively established affected architectural surface. Record unknowns rather than assuming that unmentioned context was not considered.

Compare cascade and non-cascade changes using change size, architectural centrality, boundary count, and available complexity proxies.

## Phase 7 — Before/after graph-assisted comparison

After fixing the intervention definition independently of outcomes, compare pre-graph and graph-assisted cohorts using the same metrics.

Primary prospective outcomes:
- corrective descendant rate;
- cascade depth;
- time to closure;
- first-pass architectural completeness;
- rework ratio;
- regression escape after passing original tests.

Secondary outcomes:
- throughput/change lead time;
- change size;
- proof/test selection efficiency;
- hotspot recurrence.

## Phase 8 — Robustness checks

At minimum:
- rerun headline results using Grade A edges only;
- rerun with Grade A+B;
- report exposure edges separately;
- exclude security-hardening discovery passes as a sensitivity analysis;
- stratify by PR size and subsystem;
- distinguish immediate follow-ups from long-distance corrections;
- document censored post-graph cascades due to shorter observation time.

## Reproducibility

Derived datasets should be machine-readable and generated by versioned scripts where possible. Manual classifications must preserve evidence references and classification rationale. Any rubric revision requires a version bump and sensitivity comparison against prior classifications.
